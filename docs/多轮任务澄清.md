# 多轮任务澄清

更新：现已支持 SEQUENCE 有序步骤列表、长录音和草稿确认。新功能及完整重建步骤见[任务草稿与长任务](任务草稿与长任务.md)。

本次实现将现有 ROS 音频链路扩展为多轮补充信息，不调用机器人执行接口，也没有新增 MCP 客户端或服务器。规则校验和会话保存独立于模型；后续接入 MCP 时，可以用工具包装这些能力，继续复用本模块。

## 代码如何协作

1. `AudioPipeline.accept_asr()` 保存真实识别文字，识别整句“取消任务／重新开始”等对话控制词。
2. `build_parse_goal()` 按 `(session_id, input_context_id)` 查找待补充任务，将最近对话放入 `ParseTask.Goal.context`，候选放入 `partial_candidate`。新任务这两项保持为空。
3. `OllamaBackend.parse()` 让模型结合追问补充参数；`reconcile_candidate()` 保留模型漏掉的已知字段，拒绝改变已有地点、任务类型或返回要求的续轮。模型若返回 UNKNOWN，不用旧字段拼出一个完整任务。
4. `validate_candidate()` 独立检查字段类型、必填项、互斥字段和工位／物料白名单，产生 `missing_fields` 和追问。信息缺失并不授权执行。
5. `AudioPipeline.update_dialogue()` 只缓存通过校验的 NEED_CLARIFICATION 候选。READY 清除缓存，发布完整候选；失败保留原待补充任务，取消清除当前上下文的缓存。
6. 界面显示已有信息、缺失信息及追问。用户再次点击录音回答，不需要重新说 A→B。

```text
“去 A 点拿东西，然后到 B 点放下”
  → TRANSPORT / pickup=station_a / dropoff=station_b / object=""
  → missing_fields=[object_id]
  → 保存候选，显示“要搬运哪个物料？”

看到追问后再次录音：“一号箱子”
  → 同一 session_id + input_context_id
  → 旧候选 + 历史追问 + 新回答 → 模型
  → object_id=box_1，保留 A→B
  → 字段与白名单校验通过 → READY
  → 展示完整候选，尚未执行
```

提示词明确列出 `A点/A工位 → station_a`、`B点/B工位 → station_b`、`一号箱子 → box_1` 的示例别名，只有对应 ID 在当前白名单中才可使用。没有物料名称时，即使白名单只有 `box_1`，也不能自动填入。其他实际工位、物料名称应在部署时补充明确映射。

## 上下文边界

- 每轮录音使用新的 request_id 和 segment_id，同一次澄清保留相同的 session_id、input_context_id。当前麦克风节点在一次进程运行中默认保持这两个 ID 不变。
- 只在等待补充信息时保留候选；最多 32 个待补充上下文。进程重启后清空，不从历史录音恢复任务。
- `audio_processing_node` 的 `clarification_timeout` 默认 `300.0` 秒，从最近一次追问开始计算，允许范围 `(0,1800]`。过期后第一次续轮会提示 `DIALOGUE_EXPIRED`，要求重新描述完整任务。
- 最近对话最多 6 条、800 个 UTF-8 字节，完整候选另存；原始录音、TXT 和解析 JSON 仍逐轮保存。输入过长时仍受模型适配层的上下文预算限制。
- 追问产生前就开始的录音不自动当作回答，返回 `CLARIFICATION_NOT_READY`，保留待补充候选。
- 续轮改变已有字段返回 `DIALOGUE_CONFLICT`。例如原取货点是 A，补充时改成 B，需要先单独说“重新开始”，再描述新任务。
- 单独说“取消／取消任务／取消当前任务／不用了”清除当前上下文的待补充候选；“重新开始／新任务／开始新任务”清空后提示重新描述。这些命令只管理待澄清候选，不代替未来执行层的机器人取消接口。
- READY 只表示候选完整。当前已提供独立的草稿人工确认，尚未接入机器人任务准备或执行服务；单说“确认”不会触发执行。

## 手动测试

以下命令由用户在 WSL Ubuntu 中执行。本次修改未运行构建、测试、GUI 或模型。

先在 Git 仓库目录更新代码；若仓库位于工作空间的 `src` 中：

```bash
cd ~/ai-interaction-ui/src
git pull --ff-only
cd ~/ai-interaction-ui
source /opt/ros/humble/setup.bash
colcon build --packages-select ai_edge robot_visualization --cmake-args -DAMENT_CMAKE_SYMLINK_INSTALL=OFF
source install/setup.bash
```

先关闭旧工作台及此前单独启动的同名后端节点，确保只运行一套。使用已替换为 PySide6 6.8.3 的系统 Python 启动：

```bash
ros2 run --prefix /usr/bin/python3 robot_visualization dashboard --ros-args \
  -p asr_python:=/usr/bin/python3 \
  -p audio_root:=received_audio \
  -p allowed_station_ids:="[station_a, station_b]" \
  -p allowed_object_ids:="[box_1]"
```

1. 等 ASR 和麦克风就绪，录音说“去 A 点拿东西，然后到 B 点放下”，停止录音。预期搬运候选保留 A→B，物料为“待补充”，出现追问。
2. **等追问显示后**再次录音说“一号箱子”，停止。预期新记录保留 A→B，物料为 box_1，候选完整，界面明确显示尚未执行。控制台应出现“继续澄清”“保留候选”和“候选字段完整”等消息。
3. 重复第一步，然后说“重新开始”；再单独说“一号箱子”。预期旧路线已清除，这句话不能单独生成搬运任务。
4. 重复第一步，回答“取货点改成 B 点”。如果模型提取了新地点，应返回冲突并保留原候选；不能悄悄改写取货点。若模型未理解修改，结合 TXT 和 JSON 继续检查模型输出。
5. 重复第一步，超过五分钟后回答“一号箱子”。预期超时提示，要求重新描述任务。
6. 观察 `received_audio/` 中每轮各自的 TXT 和 `.parse.json`，核对 ASR 原文、missing_fields、candidate 和相同的 session/context；不同 request_id 属于正常情况。

可选离线规则测试（同样由用户手动执行，不会调用模型）：

```bash
PYTHONPATH="$PWD/src/ai_edge${PYTHONPATH:+:$PYTHONPATH}" \
  /usr/bin/python3 -m unittest discover -s src/ai_edge/test -p 'test_dialogue.py'
```

若仓库直接放在工作空间根目录，省略上述 `cd src`，并将离线测试路径中的 `src/ai_edge` 改为 `ai_edge`。
